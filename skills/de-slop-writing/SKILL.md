# 技术文档说人话（de-slop-writing）

所有写入本地文件（如 `.md` 方案、实现计划、排查笔记、项目文档）或发布到外部系统（如飞书文档、Wiki、MR/PR 描述、Issue 描述、复盘文档等）的中文技术文档，无论读者是开发者自己还是其他人，都应该摆脱翻译腔、电报式缩写、碎片化排版和 AI 套话，写成自然、清楚、一眼能看懂的中文。

**核心要求只有一条：在不遗漏、不改动任何技术细节（接口、字段、参数、状态码、分支条件、数值、工单号等）的前提下，用符合中文母语习惯的方式把事情讲清楚。**

## 一、清理生造词、翻译腔与电报式缩写（核心重点）

中文把技术逻辑讲清楚，字数往往比英文多几个字，这不叫啰嗦。宁可多写几个字把「主语、谓语动词、宾语、触发条件」写完整，也不要为了省字数去生造缩略词，或者删掉动词写让人猜的电报体。

### 2. 把条件和动作硬压成别人解不开的复合词、电报句或单字黑话动词

#### （1）把带条件、时序和分支的完整逻辑硬压成电报式复合词

这类词通常是为了往表格、列表或小标题里硬塞，把一整句包含前提条件和先后顺序的话压成了几个字：

| 文档里常见的写法 | 自然的中文表达 |
| --- | --- |
| 建时定一次 | 创建时确定，之后不可修改 |
| 可空加读时回退 | 字段允许为空，读取时如果为空则回退到默认值 |
| 宁空勿断 / 记空不阻断 / 显空不崩 / 成对记空 | 字段缺失或解析失败时写入 `NULL`，不阻断入库；页面展示为空白且不报错 |
| 存而不显 | 数据库存了值但页面上显示不出来 |
| 同填同空 / 同成同败 / 四键恒出现 / 非枚举类型早退 | 两个字段必须同时填写或同时留空 / 在同一事务内同时成功或同时回滚 / 字典中始终包含这四个字段 / 如果不是枚举类型则直接提前返回 |
| 一包一窗，不静默扩窗 / 醒来补缺 | 每个导出压缩包严格对应一个 1 小时时间窗口，不自动合并扩大时间范围 / 定时任务每次启动时自动补齐缺失时间窗口的数据包 |
| 落窗 / 落窗列 / 落窗轮次 / 扫一次全窗 | 落在查询时间范围内的数据 / 时间范围过滤字段 / 扫描整个时间范围的数据 |
| 天任务 / 天文件 / 天窗口 / 切天 / 戳天末 | 按自然日拆分归档任务与时间范围 / 单日归档文件 / 拼接当日结束时间 `23:59:59.999999` |
| 先归档后开删 / 下轮续删 | 先完成归档再开启数据删除 / 下一轮任务继续删除剩余数据 |
| 三档分档，不串档 / 串月 / 串库 / 串对象 | 按三种类型分别处理且互不混用 / 不同月份、不同数据库或不同业务对象的数据互不混淆污染 |
| 三头协议 / 头 body 分叉以头为准 / 缺头回落默认不阻断 | 三个 HTTP 请求头的传递约定 / 请求头与请求体不一致时以请求头为准 / 缺少请求头时回退为默认值且不阻断流程 |
| 单边给出直接 400 / 0 配额也列出保全貌 | 只传起止日期中的一个参数时直接返回 400 错误 / 配额为 0 的账号也一并列出，以展示完整列表 |
| 条件失效不连坐 | 即使已有的筛选条件引用了已删除的字段，只要本次不改动筛选条件，依然允许正常保存 |
| 有列才带 / 存量死列自动复活 / 存量免迁移 / 读时现算 | 检查目标表存在该列时才在 SQL 中带上该列 / 历史已建好但未写数据的列开始自动写入数据 / 历史数据无需迁移 / 读取或导出时实时计算 |
| 缺表建、真表不动 / 单段名可达 | 目标表不存在时创建空占位视图，真实表已存在时不覆盖 / 与目标表在同一个数据库下，无需跨库前缀即可直接用表名访问 |
| 零值保真 / 三态保真 | 无数据时显式补 0 而不省略条目 / 保留 `0`、`1`、`NULL` 三种原始状态，不把未填写（`NULL`）转成 `0` |
| 直构穿透洞 / 直构拒 / 防静默解包错果 / 出错果 | 直接调用构造函数实例化对象时绕过校验的漏洞 / 直接构造非法实例时报错拒绝 / 防止调用方解包返回元组时不报错却拿到错误的值 / 产生错误的查询结果 |
| 套壳不动存量 id / 惰性套壳 / 不套壳、不刷库 | 外层包裹容器节点时不修改已有节点的 `id` / 在首次读取或编辑时才按需包裹容器节点，不批量修改存量数据库记录 |
| 短路让路 / 双轨对拍一致 / 混锅回归 / 端到端已活 | 跳过提前返回分支，继续往下执行权限策略计算 / 新旧两套参数的查询结果对比验证一致 / 循环执行任务时多次执行共用了同一个批次号，导致数据串在一起 / 整条调用链路已调通 |
| 先红后绿 / 先红 18 后绿 24 / 精确转红，恢复转绿 / 预期直接绿 | 先运行测试确认失败，编写实现代码后再运行测试确认通过（修改前 18 个失败、修改后 24 个通过）/ 临时注释校验代码确认对应单元测试能报错拦截，恢复后全部通过 / 预期直接通过 |
| 卡可取 / 下一个请求起 404 | 可以正常拉取 AgentCard / 从下一个请求开始返回 404 |
| 迁移序 / 可达环境 / 行自身键 / 低百级 / 现实现 / 区顶 | 迁移执行的顺序 / 网络能连通的环境 / 这一行记录自身的主键 / 几百条以内 / 现有的代码实现 / 根域名（Zone Apex） |
| 反挂 / 堵…复发 / 图裂 / 按粒度分桶 | 挂载方向反了 / 防止…再次发生 / 引用关系断开 / 按天或按月分组统计（不要把 *bucket by granularity* 直译成「按粒度分桶」） |

#### （2）砍半截的单字黑话动词与中英半截杂交词

| 文档里常见的写法 | 自然的中文表达 |
| --- | --- |
| 滥用「落」字造万物：`落码 / 不落码 / 产码 / 落标 / 落账 / 落值 / 落包位置 / 落库时机 / 不落日志 / 不落新列 / 落真分派 / 落档` | 写代码 / 不在代码中写死 / 写入标记 / 扣减额度入账 / 写入字段值 / 文件在压缩包中的存放路径 / 写入数据库的时机 / 不记录日志 / 不新增数据库列 / 接入实际分派逻辑 / 写入文档归档 |
| 滥用「裸」字直译 *bare / raw*：`裸 Template() / 裸 SQL / 裸 JSON / 裸 file_id / 裸穿 / 裸崩 / 裸秒级分组 / 裸 chain` | 直接调用 `Template()` / 原始 SQL 或原始 JSON / 直接暴露 `file_id` / 未捕获异常直接向上抛出 / 直接崩溃 / 直接按秒级时间戳分组 / 不使用 LangGraph 的普通调用链 |
| 把「测试能拦截报错」叫成「咬」：`测试真在咬 / 证明门会咬 / 证其真咬`（源自 *the test/gate really bites*） | 验证测试或校验规则确实生效、能拦截错误 |
| 把「固定值 / 测试验证」叫成「钉」：`钉住 / 钉死 / 钉 0 / 解钉死 / 硬钉 / 测试钉`（源自 *pin / unpin*） | 固定设为 0 / 取消测试配置中的固定值限制 / 用单元测试验证并保证该行为不变 |
| 把「Mock / Stub」叫成「桩」：`桩为通过 / 桩掉`（源自 *stub out*） | 在测试中将检查 Mock 为通过 |
| 把「断言 / 否决」砍成单字「断 / 否」：`断库表回滚`、`否「给 80 张表加索引」`、`否 FK 到 users` | 断言数据库表已回滚 / 否决「给 80 张表加索引」的方案 / 不建立指向 `users` 表的外键 |
| 过度口语化的单字动词：`从 config 掏活资源`、`在汇总层里聚掉用户`、`display_name 白拿`、`resume 轮白读`、`手补`、`喂状态色块条`、`不吐裸 JSON`、`活跃用户数跟着塌`、`会话裂成两行`、`字符串炸校验`、`AttributeError 冒栈`、`打老 server / 互打 / 打挂 / 炸流` | 从 `config` 中取出运行时实例 / 在汇总层按更高维度聚合后不再保留用户粒度 / 直接复用现有的 `display_name` 字段 / 无谓读取用不到的配置 / 手写临时补丁 / 传给组件渲染 / 不输出原始 JSON / 统计值一并偏低 / 拆成两行 / 触发校验报错 / 抛出异常堆栈 / 请求旧版服务端 / 相互调用 / 导致接口报错或流中断 |
| 在 `BASE` 块尾打 `cache_control` | 在 `BASE` 段落的末尾加上 `cache_control` 标记 |
| 中英半截杂交词：`neuter 字段类型门`、`neuter 无裸 JSON 门`、`wire 路由`、`seed 默认配置`、`做 mirror` | 不要把 `neuter`（临时注释掉某段校验逻辑以验证单元测试会报错）、`wire`（注册路由）、`seed`（写入初始数据）、`mirror`（参照实现）直接当中文及物动词去接中文宾语 |

### 3. 把英文惯用句式整句搬过来（每个字都认识，但中文不这么说话）

单看里面的每个汉字（`买到`、`表面`、`形状`、`轴`、`乘`、`承重`、`函数`、`事实来源`、`张力`）都是日常熟词，但整句话的比喻方式和语法骨架完全是英文的：

- `只买到根级自动发现` / `那多买到的是故障隔离`（直译自 *only buys us...* / *what that buys us is...*）
  改为：`这样做唯一能换来的是…` / `额外带来的好处是…`
- `两个表面的形状又恰好相反——拿冻结的小表面去共享高频变动的大表面`（直译自 *the shape of the two surfaces...*）
  改为：`对内、对外两套接口的规模和变动频率完全相反：对外接口只有几个固定端点，对内接口却在频繁迭代`
- `运行时真正的轴是 chat / function`（直译自 *the real axis at runtime is...*）
  改为：`运行时真正的区分维度是 chat 还是 function`
- `代价是前端四个调用点乘两个包`（直译自 *four call sites times two packages*）
  改为：`代价是需要在两个前端包里同步修改四处调用点`
- `模型不再是配置表的可靠事实来源`（直译自 *The model is no longer a reliable source of truth for the config tables*）
  改为：`不能再直接以 ORM 模型的定义为准来生成配置表内容`
- `真正承重的数字是本期缺口 2,300 条和带写缺口 210 条`（直译自 *The load-bearing numbers are...*）
  改为：`真正决定改造风险的核心数据，是本期相差的 2,300 条规则（其中 210 条涉及写权限）`
- `五个候选实际收敛为两个正交决策：取 label 的手段 × 输出形态`（直译自 *converge into two orthogonal decisions: A × B*）
  改为：`五个候选方案实际上取决于两个互不依赖的决策：如何获取 label，以及按什么格式返回`
- `「改不动」不靠在每个编辑工具里加判断，靠让模型手里没有那半棵树`（直译自 *doesn't rely on..., it relies on not giving the model that half of the tree*）
  改为：`为了防止模型修改只读区，我们没有在每个编辑工具里逐一加权限判断，而是从源头只把可编辑区的子树传给模型`
- `条数 /「+」/ 空区隐藏都是孩子个数的函数，局部调和会停在旧值`（直译自 *are all functions of the child count; local reconciliation would stay at the stale value*）
  改为：`卡片条数、「+」号按钮以及空面板隐藏逻辑都取决于子节点数量；如果只做局部更新，这些状态会停留在更新前的旧值`
- `这次改名只治了机器可读那一半，人读的文案还是旧说法`（直译自 *This rename only fixed the machine-readable half; the human-readable copy is still the old wording*）
  改为：`这次改名只修改了代码和 SQL 里的内部字段名，界面展示给用户的文案仍然是旧名称`
- `数据行只活在内存表与前端渲染态，没有可截获的整段下载接口`（直译自 *Data rows only live in in-memory tables and frontend render state, with no interceptable bulk download endpoint*）
  改为：`数据行仅保存在后端内存表和前端渲染状态中，没有现成的接口可以直接导出完整数据`
- `失败形态是静默的：字段名对不上时图表少一条线、卡片少一个数，接口 200、日志干净、service 单测全绿——所以这类测试非有不可`（直译自 *The failure mode is silent: ... — which makes this kind of test indispensable*）
  改为：`一旦前后端字段名不一致，接口仍会返回 200 且无报错日志，Service 层单元测试也能全部通过，只会导致前端图表漏画折线或卡片少显示指标，因此必须补充这类跨端字段校验测试`

### 4. 把研发圈习惯直接说英文的词，硬翻成生僻的词典中文

比如把 Jira `ticket` 翻成「票 / 拆票」，把测试里的 `fixture` 翻成机械行业的「夹具」，把 `recipe` 翻成做菜抓药的「配方」，把 Git `rebase` 翻成「重定基」，把 LangGraph `checkpoint` 翻成游戏里的「存档」（如 `手工读改写存档`），把 `# noqa` 屏蔽告警翻成「消音」（如 `noqa 是消音不是修好`），把 `wire protocol` 翻成「线协议」，把 `PR` 翻成「拉取请求」，把 `daemon` 翻成「精灵进程」。在中文研发团队里，这些词要么直接用英文（`ticket`、`fixture`、`recipe`、`rebase`、`checkpoint`、`noqa`、`PR`、`MR`、`handler`、`fallback`），要么用大家都熟悉的固定说法（工单、测试前置脚本/测试客户端、配置脚本、变基、状态快照、屏蔽告警、通信协议、守护进程），不要生搬词典里的冷门译法。

### 5. 自己临时造一个比喻词当术语到处用，甚至衍生出「造词家族」

Claude 写中文技术文档时有一个极隐蔽的毛病：先临时拿一个单字比喻某样东西，接着顺着这个字在全文派生出一整套「造词家族」，没看过对话上下文的人完全不知道对应代码里的哪个变量或机制：
- 把关联 ID（`unique_key` / `correlation_id`）临时比喻成「锚」，接着造出 `单锚 / 双锚 / 补锚 / 空锚 / 断锚 / 抓锚 / 镜像锚 / 出站锚 / 审计锚 / 锚回落 / 每锚封顶 50 条`；
- 把所有 `if` 校验、SQL 条件、路由拦截、单元测试统称为「门」或「守卫」，造出 `两道闸 / 入队变更门 / 字段类型门 / 无裸 JSON 门 / 聚合门 / 未配置门 / 映射门 / 门外覆写 / 假守卫 / 幂等守卫 / 守卫本身也被守`；
- 顺着 `recipe`（「配方」）或图节点概念延伸比喻，造出 `上桌前检查 / 自留地 / 切半 / 缝回 / 盖章 / 套壳 / 陪跑节点 / 暗门 / 哨兵`。

最明显的特征是：写着写着需要专门加一句「下文统称 X」，或者同一个比喻词（「闸」「门」「守卫」「锚」）在文档里一会儿指数据库字段，一会儿指路由中间件，一会儿又指 SDK 里的一个 `if` 判断。

行业里早就通用的术语和简称（如写死、回滚、灰度、幂等、熔断、心跳、死锁、缓存穿透/击穿/雪崩、压测、限流）大家都懂，正常保留；但如果是当前文档里临时发明的比喻，一律改回它真实指代的具体字段或组件（日志关联 ID、白名单、开关、路由拦截、字段类型校验、SQL 幂等条件、结构校验单元测试），并全文统一。

### 6. 词义错位与无意义的修饰词

注意避免拿中文里的同字词硬套英文原意，比如「落空」在中文里指「计划落空」，不能拿去翻译 `switch case` 的 `fall through`（直接写「这个分支会继续往下走到 `default` 分支」）。同时删掉 `物理裁切`、`黄金视口`、`硬 benchmark` 这类没有实际信息量的修饰词，去掉修饰词后意思一点没少，就直接删掉。

### 把句子写通顺的四条准则

1. **拆开塞满条件和动作的复合词。** 只要短语里包含前提条件、先后顺序或两个以上动作，就不要压成紧凑的复合词（如 `可空加读时回退`、`建时定一次`、`宁空勿断`、`先红后绿`），必须用动词和连词拆成完整的分句。**表格单元格和小标题里也一样**，如果格子里放不下，就把详细解释挪到正文里，不要靠造词省空间。（注意区分「生造缩略词」和「正常的中文名词短语」：章节标题和表格表头可以用 `具体做法`、`原因与效果分析`、`存量兼容方案` 这类自然短语，禁止写压掉谓语的电报词，但也不必把表头硬拉成二十多个字的主谓宾长句。）
2. **把动作和名词写完整，不要图省事砍成单字或口语黑话。** 无论在正文还是表格里，都不要把正常的双音节动词和宾语名词砍成半截：比如把「在 `BASE` 段落的末尾加上 `cache_control` 标记」缩成「在 `BASE` 块尾打 `cache_control`」，把「调用 `save()` 方法」缩成「调 `save()`」，把「读取规则」缩成「读规则」，把「可以拉取 AgentCard」缩成「卡可取」，把「不写入代码」缩成「不落码」，把「否定某方案」缩成「否 XX」，或者到处拿「打标记 / 挂实例 / 塞数据 / 撞上限 / 刷状态 / 吃异常 / 掏资源 / 聚掉 / 喂给 / 吐出」代替准确的动宾表达（添加标记、关联实例、写入数据、达到上限、更新状态、捕获并忽略异常、取出实例、聚合消除、传入、返回）。正文叙述里直接写「同时满足以下三个条件」「A 调用 B 后触发 C」，**严禁在中文句子里夹杂离散数学与逻辑符号（`∩`、`∅`、`∘`、`⊥`、`×`、`↔`、`∥`）、代码运算符（`??`）或箭头符号（`->`、`⇒`）来代替中文连词与动词**。
3. **同一个概念叫同一个名字，不同机制各自直呼其名。** 不要用「闸」「门」「守卫」「锚」这类模糊比喻统称不同组件；反过来，对于正经的核心概念，定好一个准确名称后就从头到尾用它，不要因为怕重复而在几个近义词之间换来换去。
4. **按「现状背景、遇到的问题、我们的做法」的先后顺序顺着写，少用倒装长句。** 破除英文「先抛结论 + 破折号插入补充说明 + `because` 倒装解释原因」的句式，把因果顺序顺过来；如果一句话里同时塞进了「做法、原因、反面例子」好几层意思，就拆成两三句独立的话，一句只讲一层意思。

## 二、清理常见的 AI 表达与排版套路

1. **装老手式的训话腔、喊口号与表演式 TDD 旁白**：删掉 `读岔一个后面全乱`、`别套用同一句`、`正好掉进上面那个陷阱`、`先把三对容易混的词切干净`、`这是本期最该记住的一条教训`、`「没写」与「做不到」必须分开，否则二期会找错人修`、`查错了用户看得见，凑答案用户看不见——这条不能破`、`守卫要用变异验证证明它真的会红，「测试通过」不算证据（RED 纪律教训，留档）` 这类居高临下给读者上课、写警句口号或自我邀功的旁白。写明测试覆盖了哪些业务分支和异常情况即可，不要把「先写了个报错的测试，再改代码让它通过，接着故意注释掉一行代码看它报错，最后再恢复通过」写成戏剧化的流水账。
2. **没信息的开场套话与结尾总结**：删掉 `值得注意的是`、`需要指出的是`、`需要注意的是`、`首先我们要明白`、`直接说结论`、`综上所述`、`总的来说`、`归根结底`、`总而言之`。
3. **套路化的对比句式和强行拔高**：`不是 X，而是 Y`、`与其说是 X，不如说是 Y`、`不仅仅是 X，更是 Y`。删掉为了显得深刻而硬凑的前半句或拔高句，直接陈述事实。
4. **每句话开头都硬塞过渡词**：删掉多余的 `此外`、`然而`、`具体而言`、`也就是说`、`换句话说`，只保留真正表示转折的「但是」「不过」。
5. **破折号（——）扎堆**：同一个段落里出现两个以上破折号，或者通篇都是「半句话——破折号——另半句话」时，按作用改成圆括号 `（）`、逗号或句号。
6. **商业黑话与夸张渲染**：把 `赋能`、`抓手`、`闭环`、`对齐颗粒度`、`心智`、`不同诉求`、`推进落地` 改回具体的研发动作；删掉 `极为震撼`、`灾难性后果`、`致命缺陷`、`完美运行`、`彻底解决`、`从根本上消除` 等渲染词，直接写客观结果。
7. **多余的包装词与弱动词**：当事实已经有明确结论时，直接写「不可行」「不能替换」，不要写 `或许可以考虑评估`；不需要强调责任方时，少用「被」字句（把「Bug 被修复了」改为「Bug 修好了」），去掉「对 X 进行 Y」这类空壳动词（把「对代码进行了重构」改为「重构了代码」）。
8. **把连贯段落切成碎片化的「加粗小标题 + 冒号」列表**：不要不管什么内容都拆成 `- **现状背景**：半句话`、`- **核心痛点**：半句话`、`- **解决思路**：半句话` 的提纲体。讲述系统现状、问题起因、排查链路和设计取舍时，优先用连贯、完整的自然段把前因后果顺下来；只有真正并列的分支条件、配置项说明或操作步骤，才使用列表。
9. **生凑多列宽表格**：如果只有两项简单对比，或者每个单元格里都要塞进两三句带条件的长话，不要硬画五六列的宽表格（这正是逼出「建时定一次」这类电报词的根源），改用带编号的分段列表把每条分支写清楚。
10. **滥用数学集合与逻辑符号代替日常中文**：严禁在普通中文正文和标题里混用 `∩`（交集）、`∅`（空集）、`∘`（函数复合）、`⊥`（正交/互斥）、`×`（笛卡尔积）、`↔`、`∥`、`⇒` 等符号来装点「形式化严谨」（例如把「指标名不能与列名重名」写成 `指标名 ∩ 列名 = ∅`，把「先执行建表再执行改名补丁」写成 `建表 ∘ 改名补丁`，把「客户自助跨表查询与行级数据隔离互相冲突」写成 `客户自助跨表 ⊥ 行级隔离`）。一律用自然中文把关系写清楚。
11. **拿政治哲学或教条词汇当技术文档小标题**：章节标题必须直白反映工程内容（如 `现状分析`、`核心问题`、`POC 验证范围`、`用户可见性要求`、`边界场景与待确认项`），严禁为了装深刻或套用人设而写出 `## 1. 调查：报表现在是怎么活的`、`## 2. 主要矛盾`、`## 4. 实践：POC 只验结构`、`## 5. 群众路线`、`## 6. 两点论` 这类荒诞标题。

## 三、文档结构的整理原则与清理多轮对话残留

### 1. 按阅读直觉重组章节结构

如果原稿是由多轮讨论或零散分析拼凑出来的（比如开头没有任何背景就先抛出一堆边缘开关表格、把核心矛盾藏在文档中后段、或者同一个机制拆在三个地方反复打补丁），在改写语言的同时，应该按符合阅读直觉的顺序重新梳理章节结构：

1. **设计背景与现状问题**：现在系统是怎么跑的、遇到了什么具体问题、涉及哪些需要先理清的核心概念。
2. **方案选择与核心设计决策**：针对核心矛盾有哪些备选方案、为什么选当前方案、关键取舍的工程原因是什么。
3. **具体实现细节与规格**：数据表字段、路由与端点规则、接口契约、鉴权与异常响应、代码改造范围与排期。

重组结构时严守一条底线：**只调整叙述顺序和归并零散片段，绝不丢失或概括掉原文的任何技术细节。**

### 2. 清除多轮对话残留与 Agent 内部脚手架痕迹

当文档是从长对话（多轮代码搜索、排障试错、方案推翻重来）整理而来时，必须保证文档**「完全脱离当前聊天记录也能独立看懂」**（无论是给别人看，还是自己过几天回头看，都不需要再去翻当时的对话过程）：

- **砍掉无效的排查弯路**：技术方案、本地设计文档和 MR 描述只写最终确认的现状、根因与方案取舍，不要按聊天时间线写成「起初我们怀疑是 A，排查了某文件后发现不是，后来又尝试了 B」（除非文档本身就是排障过程复盘）。
- **彻底清除人机对话的「你 / 我」人称与自我检讨日记体**：正式技术文档中**严禁残留第二人称 `你` 和第一人称 `我` 的聊天痕迹**（例如 `方案 A vs 方案 B：选 B（你拍板）`、`执行顺序（你批准）`、`由你在测试环境跑一遍冒烟`、`被你抓回来`、`待你抽查`、`这条我一度判断错，此处为更正`、`我原先在注释里写……实测为假`、`吃了一个 FAIL`、`打脸的地方在于 T4 是我写的`）。一律改为客观第三人称技术陈述或写明具体角色/责任人（如 `经评审确定采用方案 B`、`由工单负责人在测试环境执行冒烟验证`、`注：此前关于 X 的假设经实测不成立，原因如下`）。
- **删掉对话指代词**：全文禁止出现「如前所述」「按刚才定的方案」「上面那个表」「还是沿用老办法」等依赖聊天历史的指代，所有前置背景和涉及的模块必须在文档开头交代清楚。
- **不要把聊天里的口语简称升级成正式术语**：用户在终端提问时为了打字快随口敲的简称（如「把重算脏回写那块堵死」），在写入文件或发布到外部系统的文档里必须还原为准确的技术表述（「在批量重算汇总前剔除计算失败的记录，防止污染回写结果」），不要直接拿口语简称当章节标题或正文术语。
- **严禁泄露 Agent 内部脚手架指令、免责括号与 Token 账单**：输出或更新文档时，必须彻底剥离上游 Prompt / Skill 模板里写给 AI 自己看的占坑指令或机械解析提示（严禁在正文或标题里残留 `## 待填写标签（由流程脚本读取，勿改字段名）`、`## 3. 参数说明（自定义段落）`、`无子页时详情落这里`），删掉 AI 心虚留下的免责括号（如 `(推断，如错请纠正)`）、内部审查代号黑话（如 `R-096 钦定`、`用例 C-16.1 分句兑现`）以及运行消耗汇报（如 `本轮 token 消耗 34.2 万`）。
- **禁止版本演进「墓碑式留痕」**：当方案在多轮迭代中发生变更时，必须直接将文档正文修改为最终生效的方案；**严禁在旧章节顶部贴一段 `⚠️ 终态变更：本节契约已被取代`，底下却原封不动保留几百行已作废的旧方案**让读者自己去比对哪里改了。如果确有必要说明为什么放弃旧方案，将其简要归入「备选方案与取舍原因」小节即可。

## 四、执行工作流：写入前自检与独立 Subagent 审校

由于编写文档的主 Agent 往往刚刚经历了大量英文代码阅读、报错排查或多轮问答，极易受当前上下文惯性影响而写出上述 AI 味。在把文档写入本地文件或外部系统时，请遵循以下两级工作流：

### 1. 必选步骤：输出或写入文件前的四项自检

在输出最终文档或调用工具写入本地文件、外部系统前，必须在内部逐条核对：
1. **技术细节零丢失**：源码文件路径、类名与函数名、表名与字段名、配置键、状态码、工单号、阈值数字是否 100% 保留？
2. **表格与标题扫雷**：所有小标题和表格单元格里，是否还残留 `建时定一次`、`宁空勿断`、`真源`、`先红后绿`、`落码` 这类省掉动词的电报词或英文硬译词？
3. **句式、符号与对话残留扫雷**：是否有单段两个以上破折号 `——`？是否有 `不是 X，而是 Y`？是否把本该连贯叙述的背景切成了满屏 `- **xxx**：` 的碎片列表？正文句子里是否夹杂了 `->`、`⇒`、`∩`、`∅`、`×` 等符号？是否还残留 `你拍板`、`我一度判断错`、Skill 模板提示词或作废章节的「墓碑警告」？
4. **直接交付正文（不附带修改说明尾巴）**：如果是写入本地文件或更新外部系统文档，直接将改好后的内容写回目标位置并简短告知完成；如果在对话中直接输出，只输出改好后的完整文档正文，**严禁在文末附加「本次修改主要去除了以下 AI 表达：1. 把烤死改为了写死……」的修改说明清单**。

### 2. 按需启用：用干净上下文的独立 Subagent 审校长文档

当主 Agent 在同一会话中经历了大量代码搜索和讨论后，它对会话内临时造出的黑话和省略的背景会产生「视角盲区」。此时应根据场景复杂度，决定是否派生一个不继承聊天历史的独立 Subagent 来做审校：

如果当前会话本身就是新开启的干净上下文（例如用户直接提供了一篇现成文档要求润色），或者只是写简短的 Commit Message、几百字以内的常规 MR 描述、单处注释与局部段落修改，主 Agent 原地完成并执行上述四项自检即可，无需启动 Subagent。

遇到以下三类场景时，应当调用独立 Subagent 审校：一是当前会话已经经历了多轮代码排查、报错分析或方案拉锯，需要将结论整理成正式的技术方案、实现计划 Plan、深度排查笔记、Wiki、飞书文档或事故复盘；二是涉及跨模块调用链路与多方案取舍的长篇文档；三是用户明确反馈生成的文档「还是像 AI 写的 / 读着太累 / 没说人话」。

调用独立 Subagent 时按两步分工：
1. **主 Agent 先写出「事实完整版」初稿**：由于独立 Subagent 没有看过刚才排查过的源码，主 Agent 起草初稿时，必须把所有代码路径、函数调用关系、表字段、边界条件和前因后果全部写全（宁可多写几句大白话，绝不留只有看过聊天记录才懂的暗语或无主语缩写，防止 Subagent 因缺少源码上下文而猜错业务含义）。
2. **派生独立 Subagent 清理翻译腔并按读者视角理顺结构**：启动一个干净上下文的 Subagent，将初稿（或目标文件路径）与当前 `de-slop-writing/SKILL.md` 的实际路径交给它，并传入以下指令：
   > 请先完整读取 `<de-slop-writing/SKILL.md 的实际路径>`。你现在处于完全独立的干净上下文中，请严格遵循该 Skill 的全部准则审校并改写这份技术文档：
   > 1. 100% 保留原文中的所有代码标识符、文件路径、表名字段、配置项、状态码、工单号、数字和分支逻辑，严禁删减或自行脑补未提及的技术事实；
   > 2. 站在「不依赖刚才聊天记录、直接打开文档就能顺畅看懂」的视角，理顺倒装或碎片化的背景与因果链路，把乱切成 `- **xx**：` 的碎片列表还原为连贯自然段，清除所有人机对话人称（`你拍板`、`我判断错`）、模板占坑指令和作废墓碑段落；
   > 3. 彻底清理英文直译骨架、生造复合词/电报体、临时比喻代称（如 `锚`、`门`、`守卫`）、数学符号代连词、破折号堆砌和套路话；若遇到指代不明的残缺缩写，请结合文中已有的代码上下文或对应源码补全主谓宾；
   > 4. 直接输出（或写回）改写后的完整文档正文，不要输出修改过程说明。

**❌ 典型的 Claude 原始初稿：**

**✅ 改写后的自然中文表达：**
> 为了防止模型修改只读区，我们没有在每个编辑工具里逐一加权限判断，而是从源头只把可编辑区的子树传给模型。进入工具调用循环前，系统先把报表配置转换成标准分区结构并补齐节点 `id`，再按编辑开关拆分组件树；工具调用循环结束后，系统也只对模型修改过的可编辑区子树执行校验和节点 `id` 补齐，最后再与只读区合并回完整的报表配置。这样四个写入工具、完成信号和重新绑定工具都不需要改动原有代码，在循环内就只能看到并操作可编辑区。
>
> 在这套流程中，配置校验、补齐节点 `id` 和重新绑定数据这三步也都只处理可编辑区。第一，进入循环前的配置校验只检查可编辑区：如果只读区存在历史遗留的失效配置，模型手里并没有只读区的子树，根本无法修复该错误，一旦报错拦截就会导致整个编辑流程卡死。第二，只为可编辑区补齐节点 `id`：防止模型在编辑时意外清空节点 `id`，导致系统重新生成新 `id` 并覆盖掉只读区原有的固定 `id`。第三，判断是否需要重新绑定数据时只检查可编辑区：只有可编辑区存在数据绑定时才重新执行绑定；否则只读区锁定后，哪怕本轮编辑没有改动任何内容，也会因为只读区带有绑定关系而在每次编辑时被强制重跑绑定。

### 范文 1：需求背景与存量兼容设计（成员批量导入时自动加入部门项目组的开关）

目前通过 `server/members/importers/members.py` 批量导入更新成员（成员类型为 `employee`）时，主流程 `MemberImporter.run` 在更新完成员自身字段后，会固定调用 `MemberImporter.sync_project_membership`。该方法读取导入暂存表 `member_import_rows` 中的 `department` 字段（即导入文件里填写的「所属部门」，而非 `members` 主表上原有的部门字段），对比该成员已加入的项目组列表与这个部门名下的项目组列表。如果该部门下的某个项目组还没有这名成员，系统就会自动把这条「项目组-成员」关系补充写入 `project_members` 表，并同步写入变更历史表 `project_member_histories`。

这套自动补充机制初衷是帮管理员省去手动把成员拉进项目组的步骤，但在几家大客户的实际使用中出了问题（见 PROJ-1024）。客户管理员有时只是通过导入批量更新成员的手机号、职级等档案属性，由于导入文件里带上了「所属部门」列，系统在后台自动把这些成员加进了一批项目组；项目负责人打开项目成员列表时，发现名下平白多出了从没邀请过的人，误以为项目权限被别人改乱了。

为此，我们在模板级 JSON 配置字段 `import_templates.settings` 中新增布尔开关 `auto_join_department_projects`，按导入模板控制是否自动补充项目组关系：

1. **开关关闭（`false`）时**：`MemberImporter.run` 直接跳过 `sync_project_membership`，只更新成员自身字段以及头像同步、邮箱校验、标签处理等常规环节，不向 `project_members` 和 `project_member_histories` 插入任何记录。定时任务 `backfill_project_members`、部门调整接口 `process_department_change` 以及审批流等其他入口不受此开关影响，仍保持原有逻辑（需在上线说明中注明）。
2. **开关开启（`true`）或配置键缺失时**：保持现有补充行为不变，同时优化了 `project_members` 的写入实现。原先「先查出已软删除的记录，再分拆执行 `UPDATE` 和 `INSERT`」的两步写法在并发导入时容易引发死锁；现改为按 `(project_id, member_id)` 唯一键排序后，按 `MemberImporter.BATCH_SIZE` 的大小分批执行单条 `INSERT ... ON DUPLICATE KEY UPDATE` 语句：目标记录不存在时直接新增；已存在但处于软删除状态（`deleted=1`）时将其恢复为 `deleted=0`，并更新 `updated_by` 和 `updated_at`；已存在且未删除时保持原值不变。
3. **非法配置值拦截与存量客户平滑升级**：由于 `import_templates.settings` 是自由编辑的 JSON 字符串，如果管理员误填了 `null`、字符串 `"false"`、`"0"` 或数字等非布尔值，导入执行阶段会直接判定为配置错误，将整批导入状态置为 `fail` 并回滚，同时在每行记录上写入明确的配置错误提示。为保证存量客户升级后原有行为不变，代码读取配置时若发现该键不存在，默认按 `True` 处理，这样即使个别环境漏跑了部署脚本，行为也不会变化；同时上线时会运行 `server/scripts/deploy/` 下的幂等部署脚本，通过 Django ORM 为所有租户的 `employee` 导入模板写入 `auto_join_department_projects: true`。如果模板里已经存在这个配置键则直接跳过，不覆盖管理员手动修改过的值。

### 范文 2：方案选型与技术取舍论证（表单校验规则引擎的自定义拒绝语法与模板编译缓存）

在表单校验规则引擎的改造（PROJ-2051）中，后续需求允许客户在管理后台手写 Jinja2 模板，并在满足特定业务条件时主动拒绝本次表单提交、向前端返回自定义的拦截提示文案。改造主要涉及两个设计取舍：如何在 Jinja2 模板里主动抛出业务拒绝异常，以及编译后的模板对象缓存在哪一层。

第一，如何在 Jinja2 模板里主动抛出拒绝异常。Jinja2 本身没有内置的抛异常语句（直接写 `{% raise %}` 会在编译期报错 `TemplateSyntaxError: Encountered unknown tag 'raise'`），必须在引擎统一的 `FORM_JINJA_ENV` 环境中扩展这一能力。备选方案有两个：一是在 `env.globals` 中注册全局函数 `form_reject(msg)`；二是通过 Jinja2 Extension（`FormRejectExtension`）实现自定义语句标签 `{% form_reject '<文案>' %}`。最终选择自定义语句标签，原因有两点：

1. **避免与表单上下文中的同名变量冲突**：模板渲染时的上下文 `ctx` 由表单字段值和业务参数动态拼装而成。如果采用 `env.globals` 全局函数，一旦某个表单字段恰好也叫 `form_reject`，渲染上下文就会遮蔽全局函数，导致调用时抛出 `TypeError: 'str' object is not callable`。外层捕获这个异常后会把它当成普通的「规则计算」报错处理，导致客户编写的业务拒绝理由丢失，无法展示给前端。而自定义语句标签在编译阶段就会直接解析为 AST 节点，运行时不去查询上下文变量字典，不会和同名字段发生冲突。
2. **在保存规则时就能拦截拼写错误**：规则引擎没有引入复杂的运行时沙箱，主要依靠保存规则时的语法校验和执行前的校验来保证安全。如果客户把全局函数名拼错（例如写成 `form_rejct('...')`），Jinja2 在编译期只会把它当成普通变量调用，保存规则时的校验无法发现这一错误，直到线上真正提交表单渲染时才会抛出 `UndefinedError`；而语句标签一旦拼错，编译阶段就会直接抛出 `TemplateSyntaxError`，管理员保存规则时就能当场报错拦截。

在具体执行时，`{% form_reject %}` 标签还对提示文案做了统一校验：最大长度限制为 200 个字符（`FORM_REJECT_MESSAGE_MAX_LENGTH = 200`）；如果去掉首尾空白后为空字符串，则自动回退到 `messages.csv` 中的通用兜底提示，最后抛出状态码为 422 的 `FormRuleUserError`。

第二，编译后的模板对象缓存在哪一层。`recheck_submissions_by_rule` 批量复核每批次处理 5000 条记录（`CHUNK_SIZE = 5000`），原先每渲染一条记录都会调用 `Template(template_str)` 重新做一次词法分析和编译。改造后，所有模板渲染统一使用模块级的 `FORM_JINJA_ENV` 实例（已注册 `fmt_money` 与 `fmt_datetime` 过滤器），编译后的模板对象只缓存在当前批次函数内部的局部字典里，单批次跑完随函数返回自动释放。这里之所以不做进程级 LRU 长期缓存、也不接入平台的跨进程缓存失效广播，是因为单批次内每条规则只编译一次，就已经把 5000 次重复编译降到了 1 次，性能提升完全够用。每次发起新的复核任务或在线提交时直接从数据库重新读取规则并编译，既能避免 Celery 多进程下读到旧缓存，也省去了在规则表增删改时维护缓存失效钩子的麻烦。

### 范文 3：线上缺陷根因链路与事务边界说明（积分批量重算时单条失败污染整批回写）

线上排查会员积分批量重算任务 `recalculate_points_by_rule`（`server/loyalty/points.py`）时发现：只要同一个重算批次里有单条记录因为规则异常计算失败，不仅没有跳过该条失败记录，还会导致整批已算成功的记录在回写结果和审计明细时全部回滚丢失，但重算事件表 `PointsRecalcEvent` 的最终状态却依然显示为执行成功。

具体触发链路如下：

1. **源头写入了结构不兼容的错误占位字典**：在分块计算阶段（第 812 行），当单条记录的规则渲染抛出异常时，代码捕获异常后向结果字典写入了 `chunk_results[member_id] = {'error': str(e)}`（正常记录的值则是 `{逻辑字段名: 计算结果}` 格式的字典）；到了最后的汇总步骤，代码直接将这些带有 `'error'` 键的失败记录原封不动地合并进了 `final_results`，并且统计进了事件的成功重算条数 `recalc_record_count`。
2. **下游审计回调将 `'error'` 误判为数据库列名**：重算主流程随后通过 `RecalcCallbackRegistry` 将 `final_results` 派发给负责记录变更审计的回调 `write_recalc_audit`（位于 `server/loyalty/audit.py`）。该回调遍历结果字典中的所有键，去字段映射表 `FIELD_COLUMN_MAP` 里查找对应的数据库列；由于 `'error'` 不是合法的业务字段名，`resolve_db_column` 在映射表里查不到后触发了兜底分支，直接把字符串 `'error'` 当作数据库列名返回。
3. **整批旧值查询报错并引发事务回滚与状态假成功**：审计回调带着非法的 `'error'` 列名去批量查询本批次全部记录的数据库旧值时，SQL 执行直接报错。异常处理分支将旧值读取失败当成「旧值全部为空」，进而误判本批次所有记录的字段值都发生了变化，生成了修改前的值（`before`）全部为 `None` 的错误审计记录并尝试写入数据库；在写入数据库阶段，再次因为表中不存在 `'error'` 列而在事务块内抛出数据库异常，触发整批事务回滚。但是审计回调自身在外层用宽泛的 `try...except` 吞掉了这个异常，没有继续向上抛出，导致重算主流程误以为回调执行成功，最终把 `PointsRecalcEvent` 标记成了完成。

由于后台批量重算与在线下单对异常的处理要求不同（批量重算遇到单条失败应跳过该记录并继续处理其余记录，在线下单则需回滚整次操作并向前端报错），我们分别从两处做了修复：

- **批量重算路径（剔除失败记录并按分类统计失败次数）**：在 `recalculate_points_by_rule` 汇总 `final_results` 前，将计算失败的记录（包括规则计算异常与关联数据计算 fallback 失败的记录）从待回写结果集中剔除，不再写入空列表 `[]` 或 `{'error': ...}` 覆盖业务表原有的字段值；`recalc_record_count` 只统计真正计算成功的记录数。失败记录先按规范打印错误日志，再由 `_summarize_recalc_failures` 按「规则计算」「关联数据计算」「业务规则拒绝」三个分类汇总失败次数，写入 `PointsRecalcEvent.remark` 字段。
- **在线下单路径（用数据库事务包裹提交过程并向前端返回具体异常）**：排查时顺带发现 `submit_order`（`server/orders/orders.py:1180`）原先在积分计算还没执行前，就先把 `OrderTask` 的状态修改为 `done` 并写入了数据库。这次在 `submit_order` 内部统一加上了 `transaction.atomic()` 事务控制（覆盖 `submit_from_cart`、`submit_from_quote` 与开放 API 三条提交入口）：在线下单触发积分计算异常时，整个提交事务完整回滚，并将 `AppError`（含新增的 `PointsRuleUserError`）原样返回给前端展示具体报错信息。

### 范文 4：AI Agent 统计汇总与边界保护（数据问答 Agent 中 `query_db` 明细结果的统计摘要设计）

在数据问答 Agent 中，当 `query_db` 工具返回几十到上百行明细数据（尤其包含一对多嵌套子表）时，如果直接把原始 JSON 明细交给大模型去逐行统计数量、按维度归类或做交叉汇总，模型极易出现漏数、重复计数或把子表行张冠李戴到错误父记录上的幻觉。为此，我们在 `agent/src/tools/query_db/result_summary.py` 中新增了结果统计摘要功能：当返回的明细超过 20 行（`MIN_ROWS = 20`）时，在工具返回阶段直接用 Python 代码预先算好各列的分布与交叉统计，随明细数据一起传给模型，供模型回答统计类问题时直接引用。

具体统计与边界规则如下：

1. **列类型识别**：代码会自动跳过 `id`、`url`、`ref_id` 及所有以 `_id` / `_ids` 结尾的标识列，再根据字段的声明类型把其余列分为单选枚举、布尔、日期、数值、文本和嵌套子表。空子表和空多选列表的值都是 `[]`，所以至少要有一行的值非空、并且是带 `headers` 和 `items` 的对象，才判定为嵌套子表。
2. **枚举、布尔与文本列的汇总方式**：枚举与布尔列按取值统计精确行数。如果某个取值出现不超过 3 次（`RARE_LIMIT = 3`），还会列出对应的记录标识，方便模型在回答中直接引用具体记录。文本列（含关联对象名称列）如果在查询结果里有配对的 `xxx.id` 列，分组计数时严格按 `id` 聚合，避免把同名但不同实体的门店或客户合并成一条。某列的值全部相同时直接输出「全部为 X」；去重后不超过 8 种（`MAX_DISTINCT = 8`）时输出全量计数；超过 8 种且有重复值时，只输出出现次数最多的前 5 个取值（`TOP_N = 5`）和总种类数。
3. **日期列按天或按月分组统计，数值列不计算总和与平均值**：日期列除了输出起止范围外，会根据日期种类数和日均行数自动选择按天还是按月统计：单月内或跨月但日期种类不超过 10 个（`MAX_DAY_GROUPS = 10`）且日均记录数不少于 3 条（`MIN_PER_DAY = 3`）时按天统计，否则按月统计。**数值列不计算总和与平均值**，因为在订单明细或计量流水这类数据中，不同行往往对应不同币种或不同计量单位，机械相加没有业务意义，反而会诱导模型引用错误的总和。
4. **嵌套子表统计与数据截断保护**：针对嵌套子表，代码会同时生成三类统计：子表总行数、每个父记录下的子表行数分布（含同一父记录下子行取值是否一致），以及父表维度与子表枚举列的交叉统计表。交叉统计中会把空值（`None`）显式标为「（空）」，避免汇总时漏算空值记录。另外，**一旦检测到数据被截断，立即跳过摘要生成**：只要满足「返回行数恰好等于外层 SQL 的 `LIMIT`」「查询带有 `OFFSET` 分页」「达到服务端最大返回行数上限」或「某条父记录下的子表行数达到了 `SELECT` 子查询的 `LIMIT` 上限」中的任意一条，代码就会放弃生成对应层级或对应子表的统计摘要，防止模型把截断后的局部样本分布当成全量结论回答给用户。

### 范文 5：底层机制说明（定时任务种子数据改用 Django `bulk_create` 并跳过 `post_save` 信号）

项目里的定时任务定义存放在 `ScheduledJob` 表中，每个环境初始化时都要通过 `python manage.py seed_jobs` 写入几十条默认任务。此前 `seed_jobs` 逐条调用 `ScheduledJob.objects.create()`，每写一条都会触发模型上注册的 `post_save` 信号处理函数 `sync_job_to_scheduler`，由它立即调用调度服务的 HTTP 接口注册这条任务。在 PROJ-3107 中，我们把 `seed_jobs` 改为一次性调用 `ScheduledJob.objects.bulk_create(jobs, ignore_conflicts=True)`，重点解决了两个问题：

第一，**为什么改用 `bulk_create()`，而不是继续逐条 `create()`？**
新环境初始化时调度服务往往还没有启动完成。逐条 `create()` 会让 `sync_job_to_scheduler` 在每写一条记录后都去请求调度服务，只要其中一次请求超时，`seed_jobs` 就会在中途抛出 `ConnectionError` 退出，表里只留下前面几条任务。`bulk_create()` 只生成一条多行 `INSERT` 语句，不会触发 `post_save` 信号，写库过程不再依赖调度服务是否可用；加上 `ignore_conflicts=True` 后，按 `name` 唯一键已存在的任务会被直接跳过，`seed_jobs` 可以重复执行，不会覆盖管理员手动修改过的任务配置。

第二，**跳过 `post_save` 信号后，调度服务怎么拿到这些任务？**
调度服务启动时会调用 `load_all_jobs` 从 `ScheduledJob` 表全量加载任务定义，所以只要数据写进了表，调度服务启动或重启后就会自动注册这些任务。为了覆盖「调度服务已经在运行、之后才执行 `seed_jobs`」的情况，命令在 `bulk_create()` 完成后会额外调用一次调度服务的 `/jobs/reload` 接口；如果这次请求失败，只打印告警日志而不让命令报错退出，等调度服务下次重启时再通过 `load_all_jobs` 补上。

### 范文 6：MR Description 性能优化说明（多轮对话 Agent 的 DashScope 前缀缓存命中率优化）

**背景与问题现象（PROJ-4210）**
在 `chat_agent` 的多轮对话压测与线上耗时分析中，我们发现接入阿里云百炼（DashScope `qwen` 系列模型）后，长对话的 Prompt 缓存命中率随着对话轮次增加大幅下降：在 10 轮（共 38 次 LLM 调用）的多轮对话基准测试中，缓存命中率从第 1 轮的 58.3% 一路跌至第 10 轮的 23.6%，整场对话平均命中率只有 33.8%。随着历史消息和工具调用结果不断累积，每一轮新增的上下文都无法命中前缀缓存，导致首字延迟（TTFT）和 Token 成本明显上升。

**根因定位：DashScope 与 Anthropic 的 `cache_control` 语义相反**
此前 `chat_agent` 在组装发送给模型的消息列表时，沿用了调用 Anthropic Claude 模型时的做法，在 `System Prompt` 的 固定指令段末尾和租户配置段末尾分别加上了 `cache_control: {"type": "ephemeral"}` 标记。但在 DashScope 的隐式前缀缓存实现中，`cache_control` 的语义与 Anthropic 恰好相反：
- Anthropic 将 `cache_control` 视为「至少缓存到这个位置为止」的检查点；
- DashScope 则将请求中最后一个 `cache_control` 标记视为**可缓存前缀的上限边界**：凡是排在最后一个 `cache_control` 标记之后的消息内容，一律不进入前缀缓存。

由于我们把这个标记固定加在了开头的 `System Prompt` 末尾，排在 `System Prompt` 后面的整段多轮历史对话（`HumanMessage`、`AIMessage` 以及 ReAct 循环内产生的 `ToolMessage`）全部落在了标记之后，被 DashScope 排除在缓存范围之外。轮次越多，`System Prompt` 占总输入 Token 的比例越小，整体缓存命中率自然越低。

**备选方案实测对比与最终改动**
我们基于同一组 10 轮（38 次调用）多轮对话脚本，对三种方案做了实测对比：

| 方案 | 具体做法 | 10 轮平均缓存命中率 | 原因与效果分析 |
| --- | --- | --- | --- |
| 原方案（基线） | 在 `System Prompt` 的 固定指令段末尾和租户配置段末尾分别加上 `cache_control` 标记 | 33.8%（从第 1 轮的 58.3% 降至第 10 轮的 23.6%） | 该标记限制了可缓存前缀的上限位置，`System Prompt` 之后的全部多轮对话历史均无法进入缓存。 |
| 备选方案：在最新一条 `HumanMessage` 上添加标记 | 去掉 `System Prompt` 中的标记，改为在当前轮次最后一条 `HumanMessage` 上添加 `cache_control` 标记 | 86.9% | 在单轮 ReAct 多步工具调用内循环中，该标记固定在用户提问消息上，同一轮后续多步追加的 `AIMessage` 与 `ToolMessage` 仍然排在标记之后、无法进入缓存；而且 `langchain-openai` 的 `_sanitize_chat_completions_content` 函数会自动剔除 `ToolMessage` 内容块上的额外字段，因此也无法在 `ToolMessage` 上添加该标记。 |
| **最终方案：纯隐式缓存** | **移除所有显式 `cache_control` 标记，完全交由 DashScope 隐式前缀匹配** | **95.2%** | 不需要手动指定缓存边界位置，`System Prompt`、多轮历史对话以及 ReAct 循环内已完成的工具调用步骤全部自动纳入最长公共前缀匹配。 |

因此，我们直接移除了 `chat_agent` 消息组装链路中针对 DashScope 模型的显式 `cache_control` 标记；只要保持每轮消息块的拼装顺序固定不变，多轮对话与 ReAct 内循环就能全程命中 DashScope 的隐式前缀缓存。
